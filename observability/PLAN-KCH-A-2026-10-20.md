## 1. What the modules were (evaluated 2026-10-20)

All 12 packages on KC Hockey were read. Most leave, and two findings change
the plan.

- **Only `droost_theme` and the recipe are site code.**
  - `droost_theme` has no droost dependency, and KC Hockey's theme is a
    sub-theme of it.
  - The one thing the built site rendered from a droost module is
    `droost_examples:example_card`, through droost_cms's `event` display.
- **DO4 does not bind a fresh site.** ui_patterns 2.0.22 ships
  `ComponentPluginManagerPass`, which stops decorating `plugin.manager.sdc`
  once Canvas has replaced its class (read in United's copy), and droost_cms
  requires `^2.0.22`. `droost_canvas`'s bridge (`SdcAliasBridgePass`, 25
  lines of logic) is a no-op there. That reading is a claim; §3 probes it.
- **The Canvas tooling has no replacement on the new droost.** An agent
  loses:
  - the component registry (placeable ids, slots, versions, the props a
    template never reads);
  - `tree_get`, `tree_validate` and `tree_set` (a validated,
    all-or-nothing write of a page's component tree);
  - `component_lint`;
  - the component-tree contract (`droost_canvas/docs/component-tree-contract.md`);
  - `droost_display_compose`, cited in 33 of KC Hockey's files.

  The new pack covers this with one sentence ("built in the site … and
  exported"), `sdc_markup`, and house rules HR1 and HR2.

| Package | Verdict |
|---|---|
| `droost_theme` | **Keep** |
| `droost_cms` | **Keep, rewritten** (§2), and it ships the layer |
| `droost_canvas` (bridge) | Drop for a fresh site (ui_patterns ≥ 2.0.22) |
| `droost_canvas` (tools), `droost_ui_kit` (compose) | **Ported into the layer** (§2) |
| `droost_examples` | Drop, with the event display moved to `droost_theme:section` |
| `droost`, `droost_workflow` | Drop: `droost code:*` and `workflow:*` |
| `droost_snyk` | Drop: a `cmd:` gate if wanted |
| `droost_eca`, `droost_ai`, `droost_tool_api`, `droost_devel`, `droost_ui_patterns` | Dead off Drupal |

## 2. Decisions (owner, 2026-10-20)

| # | Decision |
|---|---|
| K1 | **droost_cms ships the Drupal CMS / Canvas layer**, the way a client layer ships its own: files scaffolded into `droost/` and `.claude/` through `extra.drupal-scaffold.file-mapping`, and an `examples/droost.yml` block merged by hand. The recipe and its agent layer move together. **As built:** not a scaffold mapping. Drupal CMS unpacks a recipe when it is required (the recipe leaves the lock), so a package file mapping would never run again; the layer is `layer/`, and `scripts/install-layer.sh <project>` copies it, never overwriting a changed file |
| K2 | **The layer carries knowledge, lint and a tree write.** It includes a skill and the tree contract, a `component_lint` gate file, and a script for a validated tree get, validate and set, run through `drush php:script`. droost itself still calls no drush (decision 2): the layer does, and it is the layer's |
| K3 | **KCH-A run 1 is autonomous** (decision 17). The owner is the client through the intake and its approval; after that, the agent answers every hold. Autonomous is set from the operator's terminal |

## 3. The work, in order

### 3a. droost_cms, branch `off-drupal`

1. **Remove the module shape:**
   - `composer.json` requires only `drupal/droost_theme`,
     `drupal/drupal_cms_starter` and `drupal/ui_patterns ^2.0.22`;
   - `recipe.yml` installs `droost_theme`, `ui_patterns` and
     `ui_patterns_field_formatters`;
   - the comments about the write gates and the bridge go.
2. **The event display** renders through `droost_theme:section` (an optional
   heading and a `content` slot, `example_card`'s exact shape), so it no
   longer depends on `droost_examples`.
3. **The layer** (`scaffold/`; as built, `layer/`, copied by
   `scripts/install-layer.sh`, the contract at
   `.claude/skills/canvas-build/component-tree-contract.md`, the PHP under
   `droost/gates/lib/canvas/`):
   - `.claude/skills/canvas-build/SKILL.md`: how a page is built (the
     registry, a tree, validate, set, export), and when a display is
     composed instead;
   - `droost/canvas/component-tree-contract.md`, re-verified on the Canvas
     version the starter pins today (the old capture is Canvas 1.7.1);
   - `droost/bin/canvas` → `drush php:script`. Its verbs are `components`,
     `tree:get`, `tree:validate`, `tree:set` and `lint`, ported from
     `TreeManager`, `ComponentLinter` and `TwigBehaviorReader`. It writes
     JSON on stdout and exits non-zero on a refused tree;
   - `droost/gates/component-lint.php`: passes on 0 and fails on 1. A Canvas
     that is absent, or a drush that cannot boot, reads as did not run
     (exit 3). As built, no custom SDC exits 4, a labelled pass (F-340);
   - `droost/agents.md`: three lines naming the skill and the script;
   - `examples/droost.yml`: the gate, the `sdc_markup` house rule and the
     render rule.
4. **Its own checks:**
   - a `validate-scaffold.php` modelled on DRUP's sections 1, 2, 4, 5 and 8
     (as built, `scripts/validate-layer.sh`);
   - `assert-recipe-applied.sh`, rewritten for the new install list.
5. **Proof on the bench** (a scratch droost_cms, never the subject):
   - the recipe applies the **first** time, with Canvas and ui_patterns
     2.0.22 and no `droost_canvas`, and a Canvas page saves and renders
     (DO4's probe);
   - the scaffold lands in `droost/` and `.claude/`;
   - `tree:set` refuses a bad tree, and the page is unchanged afterwards;
   - the lint gate fails on a broken component.

### 3c. Build the subject: `<site>`

This is a new path. The probes default to `contrib/droost/kchockey` and
write test content, so the subject does not live there.

1. `ddev config --project-type=drupal11`, then `composer create-project
   drupal/cms`, then droost_cms from its branch (a host `path` or `vcs`
   repository) and `allowed-packages`.
2. `drush site:install` with the droost_cms template, then
   `config:export`.
3. droost in `tools/droost/` (`dev-off-drupal`, the composer block from the
   roadmap's another subject runbook), then `droost init`, `droost code:index` and
   `droost code:wiki`.
4. Merge droost_cms's `examples/droost.yml`. Install Playwright in the
   container.
5. Check it: `droost doctor`, then `verify-freshness.sh` (`WF_BRANCH` and
   `ENG_BRANCH` set to `off-drupal`). Count content with `entityQuery`.
   `git init`, commit, and tag **baseline 0**.

### 3e. The round

## 4. What this round answers

The three questions, plus this layer's own:

- Did `component_lint` **measure** a component? A page with no component
  must not read passed.
- Was the agent **forced** through the tree write's validation, or could it
  write `component_tree` some other way unseen? Does the guard record
  that?
- Does `plan_grounded` hold with the layer's skill present, and are
  `code:wiki` and `code:tree` still the two looks it requires?
